## Authority rule
These invariants are a server-side working baseline for all PCMMAD lab work. Project-specific doctrine may add stricter rules, but should not silently weaken these rules. Conflicts must be surfaced, not smoothed over.

## Universal operating invariants
- Preserve continuity: maintain current state, next steps, doctrine snapshot, revisit ledger, trace matrix, live shadow, and design thread stream when the project uses them.
- Distinguish verified, provisional, inferred, and speculative claims.
- Inspect before mutation; plan before mutation; report exact paths/results after mutation.
- Never claim writes, execution, registration, ingestion, extraction, or verification unless a tool result confirms it.
- Treat compact schema limits as action-import limits, not server capability limits. Use internal tools/result handles for larger capability.
- Prefer local/server-side execution, search, storage, and readback over dumping large content into chat.
- Preserve append-only and lineage discipline for doctrine/corpus/state surfaces.

## Universal CSC invariants
- Run the finalizer after every task; remediate findings before reporting.
- Gates must distinguish submitted, started, completed, failed, timed out, registered, and promoted.
- CSC tools must not hardcode stale project names or hidden assumptions.
- New server capabilities require tests/gates when practical and must not break schema-authority gates.
- Freshness/docctrine surfaces must be refreshed or updated after mutation when required by project SOP.

## Universal code-quality invariants
- Prefer small, composable modules with explicit boundaries over giant implicit scripts.
- Do not import heavy optional dependencies at server app import time; use lazy import/subprocess probes.
- Centralize JSON serialization and readback/window semantics.
- Use project-root scope checks for file, archive, and execution paths.
- Make timeouts and output caps explicit; defaults should not kill long-running lab jobs.
- Return consistent envelopes for subprocesses and long jobs: ok/status/return_code/stdout/stderr/truncation/duration/error.
- Avoid mutable global state unless it is explicitly a registry/cache with documented lifecycle.
- Keep tests from generating enormous diffs/readbacks.

## Language-agnostic style invariants
- Names should reveal intent.
- Errors should be structured and actionable.
- I/O, parsing, execution, and mutation boundaries should be narrow and testable.
- Determinism is preferred for build/test/gate surfaces.
- No silent catch-and-pass around integrity, path safety, schema, or persistence failures.

## Language notes
- Python: prefer typed dataclasses/TypedDicts/Mapping boundaries; avoid import-time heavy model loads; use pathlib; use subprocess with shell=False.
- Rust: prefer explicit Result types, small crates/modules, deterministic tests, and no panics at trust boundaries.
- JavaScript/TypeScript: prefer typed schema validation at boundaries, explicit async error handling, and no hidden global mutation.
- C/C++: prefer bounded ownership/lifetime rules, deterministic allocation boundaries, and explicit error return conventions.
